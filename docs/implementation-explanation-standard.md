# 人类可读实现原理解释规范

> 版本：0.1
>
> 更新日期：2026-08-20
>
> 建议文件名：`HOW_IT_WORKS.md` 或 `实现原理.md`

## 1. 规范目标

本规范用于指导 AI 为软件项目编写人类可读的实现原理说明。它位于使用文档与源码之间：不要求读者深入类、函数和局部算法，也不追求详细到足以一比一复刻代码，而是帮助读者建立准确的系统心智模型。

读者阅读后，应当能够理解：

- 项目由哪些主要能力组成；
- 每项能力为什么存在、在什么位置发挥作用；
- 主要输入如何经过系统并产生结果；
- 关键判断由程序、AI、外部系统还是人类作出；
- 状态和副作用由谁拥有；
- 异常、失败和高风险情况如何收口；
- 当前实现有哪些重要限制；
- 如需继续追溯，应从哪些源码入口开始。

本规范不替代：

- README、安装教程和用户手册；
- API、配置项和类型参考；
- changelog、提交记录和设计决策记录；
- 详细到足以让 AI 复刻代码的「文字开源」规格；
- 源码本身。

## 2. 文件格式

原理说明应以 Markdown（`.md`）作为主格式。

Markdown 适合作为唯一的人类说明源，因为它同时具备：

- 清晰的标题、分段、列表、表格和代码引用能力；
- GitHub 直接渲染能力；
- 适合 Git diff 和代码评审；
- 便于 AI 读取、维护和局部更新；
- 可以通过 HTML 注释附加机器可读元数据，而不干扰正文。

不建议使用 `.txt` 作为主格式，因为它缺少稳定的结构表达；不建议使用 `.json` 作为正文，因为它不适合连续阅读。项目需要自动校验时，可以从 Markdown 提取元数据，或者另行生成 JSON 索引，但 Markdown 始终是人类可读内容的来源。

## 3. 核心原则：最少充分解释

> 每个模块必须提供理解其作用所需的最少充分解释；触发条件、判断规则、失败处理、状态、副作用、时序和能力边界，仅在它们会改变读者对行为的预测时出现。

“最少”要求删除模板化填充、源码复述和不能增加理解的信息。

“充分”要求保留使读者能够正确预测主要行为、异常行为和重要后果的信息。

不同模块允许具有不同篇幅和结构：简单转换可能只需要一段，普通功能可能需要三四个说明项，安全或持久化机制可能需要完整的条件、分支、失败和边界说明。结构差异不是不一致；统一的信息选择原则才是一致性。

## 4. 规范用语

本规范使用以下约束词：

- **必须**：不满足时，说明不能被认为完整或可靠；
- **应当**：默认采用，只有存在明确理由时才省略或替换；
- **可以**：根据项目需要选用；
- **禁止**：容易造成错误理解或无效赘述，不应出现。

## 5. 解释对象与层级

说明应围绕人类能够识别的作用和机制组织，而不是围绕源码目录组织。

推荐层级为：

```text
项目
└── 子系统
    └── 功能模块
        └── 处理步骤、状态或判断分支
```

### 5.1 项目

项目层说明整体目标、主要输入和输出，以及各子系统如何协作。它只建立全局认知，不展开局部实现。

### 5.2 子系统

子系统是一组共同承担较大职责的功能，例如命令安全、会话存储、插件加载或用户界面。子系统说明应回答：

- 它对项目承担什么职责；
- 输入来自哪里；
- 结果交给谁；
- 包含哪些主要功能模块。

### 5.3 功能模块

功能模块是原理说明的基本单位，例如命令快速筛选、删除范围预演、AI 意图复核、人工确认和审计记录。

每个模块只解释一个可独立理解的主要作用。可以分别修改、替换、失败或具有不同风险边界的作用，应当拆成不同模块。

### 5.4 处理步骤、状态和判断分支

模块内部根据真实运行关系选择表达形式：顺序步骤、判断表、状态转换、事件列表、并发参与者或生命周期。禁止为了套用模板而把非线性系统伪装成线性流程。

## 6. 所有模块的最小核心

任何值得进入原理说明的模块，都必须使读者获得以下四类信息：

1. **作用**：它解决什么问题或提供什么能力；
2. **位置**：它在系统的什么位置、阶段或关系中发挥作用；
3. **机制**：它大体如何实现该作用；
4. **结果**：它产生什么结果、状态变化或对其他模块的影响。

这四类信息不要求对应四个固定标题。简单模块应当自然地合并为一至三段。

例如：

```markdown
### 主题切换

主题切换让用户在浅色、深色和跟随系统三种显示模式之间选择。它位于界面设置层，用户的选择保存在本地设置中。

界面启动时读取该设置，并把对应主题应用到页面根节点。选择“跟随系统”时，界面监听操作系统的颜色偏好变化并同步更新。主题切换只影响显示样式，不修改业务数据和会话状态。
```

这段说明已经包含作用、位置、机制和结果，不需要再添加空洞的“判断规则”或“失败处理”章节。

## 7. 条件性解释维度

以下维度不是固定模板。只有满足右侧条件时，才应加入正文。

| 解释维度 | 加入条件 |
| --- | --- |
| 触发条件 | 功能并非始终运行，或只在特定模式、事件、用户、平台下生效 |
| 输入与输出 | 来源或去向不明显，或跨越模块、进程、网络、存储边界 |
| 处理步骤 | 顺序影响结果，或存在三个以上相互依赖的阶段 |
| 判断规则 | 相同输入可能进入多个具有实质差异的结果分支 |
| 状态与生命周期 | 功能保存状态，或存在创建、更新、过期、销毁过程 |
| 副作用 | 功能修改文件、数据库、外部系统、权限、进程或用户可见状态 |
| 失败处理 | 功能可能失败，且失败后果不明显或会影响其他模块 |
| 重试与恢复 | 失败后可能重试、回滚、降级、恢复或继续执行 |
| 并发与时序 | 先后顺序、并行、竞态、锁、超时或取消影响正确性 |
| 权限与信任 | 涉及授权、敏感数据、外部输入或多个信任主体 |
| 性能特征 | 性能是设计目标，或存在有意义的快速路径和慢速路径 |
| 能力边界 | 读者可能合理地高估能力，或存在重要未覆盖场景 |
| 设计取舍 | 当前方案牺牲了重要能力，或采用了不直观的实现 |
| 实现入口 | 读者可能需要追溯源码，且存在稳定的关键入口 |

条件不成立时，必须完全省略对应内容。禁止出现：

```markdown
#### 失败处理

无。
```

也禁止通过“没有特殊判断”“暂无限制”等句子制造形式上的完整。

## 8. 内容纳入测试

AI 在加入一段解释前，必须进行以下判断。

### 8.1 预测测试

删除这项信息后，读者是否仍能正确预测功能的行为？

如果删除后会使读者误判普通、异常或高风险情况下的结果，该信息必须保留。

### 8.2 后果测试

这项信息是否涉及不可忽略的后果，例如：

- 删除或覆盖数据；
- 修改数据库；
- 扣款或发送消息；
- 启动外部进程；
- 修改权限；
- 暴露敏感信息；
- 触发重试或重复执行。

存在重要后果时，即使实现简单，也应说明副作用、授权或失败结果。

### 8.3 非显然性测试

这项信息能否从标题、上一段或常规技术行为中直接推断？

能够直接推断的信息应当删除。只有满足以下至少一项时才保留：

- 删除后会导致错误预测；
- 删除后会隐藏重要风险或副作用；
- 删除后会隐藏模块间的重要关系；
- 删除后会隐藏不直观的设计选择。

## 9. 按代码类型选择解释结构

AI 应先识别模块类型，再选择解释维度和表达形式。一个模块可以同时属于多个类型，但不应重复相同事实。

### 9.1 简单转换

适用于格式化、字段映射、单位换算和文本归一化。

通常说明：

- 转换目的；
- 高层转换方法；
- 结果及必要限制。

通常不需要触发条件、失败处理和详细步骤。

### 9.2 流程编排

适用于订单创建、文件上传、认证、命令保护和发布流程。

通常说明：

- 触发点；
- 有顺序的主要阶段；
- 重要分支；
- 完成和失败结果。

### 9.3 判断或策略

适用于风险分级、权限检查、路由选择、推荐排序和审批策略。

通常说明：

- 判断目的；
- 判断依据；
- 结果分类；
- 每种结果的后续处理；
- 无法判断时的行为。

### 9.4 状态管理

适用于会话、任务、缓存、购物车和用户设置。

通常说明：

- 状态由谁拥有并保存在哪里；
- 谁可以修改；
- 重要状态转换；
- 过期、清理和重启恢复方式。

### 9.5 用户界面

通常说明用户能做什么、界面状态来自哪里、操作如何影响业务状态，以及重要的加载、空白、错误和不可逆确认状态。禁止用组件树和 CSS 文件清单代替交互原理。

### 9.6 数据持久化

通常说明保存内容、读写时机、一致性要求、写入失败后果、恢复和迁移方式。持久化失败会影响数据真实性时，失败处理是必须信息。

### 9.7 外部服务集成

通常说明调用时机、交换信息的性质、返回结果用途、超时和不可用处理、是否重试、是否可能重复执行，以及哪一侧是最终事实来源。

### 9.8 后台任务与并发

通常说明启动方式、并行关系、顺序保证、重复处理防护、取消、重试和重启恢复。禁止把同时发生的路径强行写成单一线性流程。

### 9.9 插件与扩展机制

通常说明挂载点、生命周期阶段、提供或修改的能力、宿主依赖、卸载清理，以及插件不存在时的宿主行为。

### 9.10 安全与权限

必须优先说明保护对象、信任主体、判定依据、允许/拒绝/转人工条件、无法判断时的行为、不可绕过条件和剩余风险。

### 9.11 算法

通常说明优化目标、高层方法、适用原因、复杂度或质量取舍，以及表现较差的输入类型。禁止把伪代码逐句翻译成自然语言。

### 9.12 构建与生成工具

通常说明输入来源、生成产物、运行时机、哪些产物不能手工修改、如何重新生成，以及失败是否会留下部分产物。

## 10. 运行关系的表达方式

### 10.1 线性流程

存在真实先后关系时使用编号列表或简单流程图：

```text
接收请求
    ↓
验证输入
    ↓
保存数据
    ↓
返回结果
```

### 10.2 分支流程

三个以上互斥结果应优先使用决策表：

| 条件 | 结果 |
| --- | --- |
| 无风险 | 自动放行 |
| 可解释风险 | 进入复核 |
| 高风险 | 等待人工确认 |

### 10.3 事件驱动

按事件分别解释其触发、处理和结果，不应虚构固定的端到端顺序。

### 10.4 状态机

状态变化影响行为时，使用状态转换表：

| 当前状态 | 事件 | 下一状态 |
| --- | --- | --- |
| 等待中 | 工作进程领取 | 执行中 |
| 执行中 | 成功完成 | 已完成 |
| 执行中 | 可恢复错误 | 等待重试 |
| 执行中 | 不可恢复错误 | 已失败 |

### 10.5 并发流程

分别说明每个参与者的职责，再说明它们通过什么事件、队列、锁或共享状态协调。时序只在影响正确性时展开。

### 10.6 插件链和中间件

说明介入顺序，以及每个环节可以继续、拒绝、修改还是暂停处理。

### 10.7 循环和持续运行

说明循环何时开始、每轮做什么、何时停止、如何取消，以及如何避免无限运行。不要重复描述每一轮相同操作。

## 11. 模块拆分规则

满足任意一项时，应考虑拆成不同模块：

- 解决不同问题；
- 触发条件不同；
- 可以分别修改或替换；
- 一个功能失败不会阻止另一个功能工作；
- 由不同主体作出判断；
- 一个功能的输出是另一个功能的输入；
- 风险、状态或能力边界不同；
- 某项作用本身已有三个以上重要阶段。

满足以下情况时，不应继续拆分：

- 只是局部辅助函数或数据转换；
- 只是某一步内部算法；
- 单独拿出来无法说明人类可理解的作用；
- 替换它不会改变读者对系统行为的预测；
- 只能用私有函数、临时类型或代码语句描述。

## 12. 详细程度

### 12.1 必须保留的信息

- 功能存在的原因；
- 介入系统的时机或位置；
- 重要输入来源和结果去向；
- 影响结果的执行顺序；
- 状态所有者；
- 判断主体；
- 允许、拒绝、降级和转人工条件；
- 重要副作用；
- 非显然失败结果；
- 安全、数据和兼容性边界。

### 12.2 通常省略的信息

- 私有函数、临时变量和完整类型字段；
- 循环、条件语句等局部代码结构；
- 测试实现和覆盖率数字；
- CSS 和局部界面布局；
- 可从文件名直接推断的职责；
- 第三方库的普通调用方式；
- 不影响行为的重构细节。

### 12.3 替换测试

如果内部技术被另一种实现替换，但功能、顺序、失败方式和能力边界不变，这段说明是否仍然成立？

如果函数改名或局部重构就使说明失效，通常写得太细。

### 12.4 预测测试

读者看完后，应能预测普通输入、异常输入和高风险输入的主要结果。如果不能，通常写得太粗。

## 13. 排版规范

### 13.1 标题

标题层级原则上不超过四层：

```markdown
# 项目实现原理
## 子系统
### 功能模块
#### 必要的解释维度
```

更深关系使用列表、表格或拆分模块表达。

### 13.2 段落

每段只表达一个主要意思。作用、流程、失败和限制如果相互独立，应当分段。

### 13.3 列表

同一列表必须表达同一种信息。列表最多嵌套两层，超过两层应改用独立小节或表格。

### 13.4 编号

只有存在真实顺序时才使用编号。并列能力使用无序列表。

### 13.5 表格

表格适合互斥判断、责任分工、状态转换和输入输出映射，不适合承载长段说明。

### 13.6 总流程与模块说明

每个复杂子系统应先给出一次总流程，再分别解释模块。总流程只说明顺序和关系，模块内部原理只在所属章节解释一次。

## 14. 语言规范

### 14.1 明确主体

应写：

```text
程序解析器确定命令结构。
AI 模型确认命令是否符合原意。
人类决定是否接受高风险后果。
```

禁止用“系统智能处理”“必要时判断”等模糊说法隐藏责任主体。

### 14.2 表达因果

应说明为什么某种设计产生某种效果，而不是只给出宣传性结论。

应写：

```text
普通命令只经过进程内扫描；只有可疑命令才启动辅助解析进程，因此日常路径几乎不承担进程启动开销。
```

不应写：

```text
该模块性能很好。
```

### 14.3 描述当前状态

正文描述当前实现，不记录“之前、后来、本次新增”等修改历史。历史属于提交、changelog 或决策记录。

### 14.4 区分事实、目的和推测

实现事实和已确认的设计目的可以写入正文。无法从源码、配置或明确要求确认的推测，不得伪装成事实；必要时标记为“待确认”。

## 15. 防止赘述

### 15.1 禁止标题复述

不合格：

```markdown
### 风险分级

风险分级模块负责对风险进行分级。
```

合格：

```markdown
### 风险分级

系统根据操作类型、目标范围和解析可靠性，把命令分为可自动复核和必须人工确认两类。
```

### 15.2 禁止跨模块重复

一个事实应有一个主要说明位置。其他模块只说明它们如何使用该事实，并通过链接或模块名称引用。

### 15.3 禁止源码逐句翻译

不应写函数调用顺序；应写人类可理解的功能阶段。函数和文件名称只放在可选的“实现入口”。

### 15.4 禁止无意义完整性

完整性来自“所有会改变行为预测的信息都已说明”，不是“所有模板标题都已出现”。空章节必须删除。

### 15.5 禁止宣传代替机制

“高效、安全、智能、可靠”等词不能独立证明任何能力。应写出产生这些性质的具体机制和仍然存在的限制。

## 16. 安全关键功能的附加要求

涉及删除、权限、资金、凭据、持久化和外部执行的模块，必须说明：

- 保护对象；
- 信任主体及其责任；
- 允许、拒绝和转人工条件；
- 解析或判断失败后的行为；
- 不可绕过的限制；
- 仍然存在的风险。

安全说明禁止只描述成功防护，不描述防护失效和剩余风险。

## 17. 源码可追溯

模块可以在末尾列出一至五个稳定源码入口：

```markdown
#### 实现入口

- 总体编排：`src/engine.ts`
- 命令识别：`src/lexer.ts`
- 范围预演：`src/preview.ts`
```

需要自动校验时，可以加入不影响阅读的隐藏元数据：

```markdown
<!-- explanation-module
id: command-preview
sources:
  - src/preview.ts
  - src/engine.ts
depends-on:
  - command-screening
  - command-parsing
-->
```

工具可以据此检查路径是否存在、源码修改可能影响哪些说明模块，以及已删除功能是否仍留在文档中。

不建议依赖行号。也不建议把完整文件哈希作为唯一有效性依据，因为格式化和局部重构会制造大量无意义过期。

## 18. 维护流程

AI 修改代码前，应先读取现有原理说明。完成修改后，应判断本次变化是否改变：

1. 模块存在性或职责；
2. 触发条件；
3. 处理顺序；
4. 判断规则；
5. 状态所有权或生命周期；
6. 输出、副作用或外部关系；
7. 失败和恢复行为；
8. 性能特征；
9. 权限、风险或能力边界；
10. 源码入口。

只有发生上述变化时才更新相关模块。AI 必须：

- 保留未受影响模块的原文；
- 只修改行为发生变化的部分；
- 描述修改后的当前状态；
- 不写提交历史和开发过程；
- 检查总流程与模块说明是否一致；
- 检查失败处理和能力边界是否仍然准确。

## 19. 自适应写作流程

AI 为一个功能编写说明时，应按以下顺序选择内容：

```text
该功能是否影响主要行为、状态、风险或模块关系？
    │
    ├─ 否：不进入原理说明
    │
    └─ 是
         ↓
用最短篇幅说明作用、位置、机制和结果
         ↓
是否有非显然触发条件？────是──→ 补充触发条件
         ↓
是否存在多个实质结果？────是──→ 补充判断规则
         ↓
是否保存或修改状态？──────是──→ 补充状态与生命周期
         ↓
是否存在重要副作用？──────是──→ 补充副作用
         ↓
失败后果是否非显然？──────是──→ 补充失败处理
         ↓
是否涉及并发、重试或取消？是──→ 补充时序与恢复
         ↓
读者是否可能高估其能力？──是──→ 补充能力边界
         ↓
是否需要继续追溯源码？────是──→ 补充实现入口
```

## 20. 自适应模板

以下模板是可选项集合，不是要求全部保留的表单。写作时必须删除不适用的标题。

```markdown
# 项目实现原理

## 项目整体如何工作

说明项目目标、主要输入、主要输出和各子系统关系。

## <子系统名称>

说明子系统职责、输入来源、结果去向和主要模块。

### 整体流程

仅在存在有意义的整体关系时使用流程图、事件列表或状态图。

### <功能模块名称>

用最少篇幅说明作用、位置、机制和结果。

#### 触发条件

仅在功能并非始终运行时保留。

#### 输入与输出

仅在来源、去向或边界不明显时保留。

#### 处理过程

仅在顺序影响结果时保留。

#### 判断规则

仅在存在多个实质结果时保留。

#### 状态与生命周期

仅在保存或转换状态时保留。

#### 副作用

仅在存在重要外部影响时保留。

#### 失败与恢复

仅在失败后果、重试、回滚或降级不明显时保留。

#### 并发与时序

仅在顺序、并行、超时或取消影响正确性时保留。

#### 能力边界

仅在读者可能高估能力或存在重要限制时保留。

#### 实现入口

- `src/example.ts`
```

## 21. 复杂机制示例结构

命令安全插件可以采用以下结构：

```text
项目整体原理
└── 命令保护系统
    ├── 模式门控
    ├── 命令快速筛选
    ├── PowerShell 语法解析
    ├── 删除范围预演
    ├── AI 意图复核
    ├── 风险分级
    ├── 人工确认
    └── 审计记录
```

总流程可以表达为：

```text
AI 发出命令
    ↓
模式与工具门控
    ↓
轻量危险信号扫描 ──普通命令──→ 直接放行
    ↓ 可疑命令
语法解析与范围预演
    ↓
AI 意图复核
    ↓
自动放行 / 直接拒绝 / 人工确认
    ↓
审计记录
```

每一项作用分别解释。总流程不重复各模块内部规则，各模块也不重复其他模块的处理过程。

## 22. 验收标准

一份合格的原理说明，应使第一次接触项目的读者能够：

- 用自己的话说明项目整体如何工作；
- 列出主要子系统和功能模块；
- 复述一条核心输入到输出的路径，或解释主要事件/状态关系；
- 说明关键判断由谁负责；
- 预测普通、异常和高风险输入的主要结果；
- 说明关键步骤失败时系统如何收口；
- 指出重要状态、副作用和能力边界；
- 知道从哪些源码入口继续追溯；
- 无需记住具体类、函数和局部算法。

出现以下情况时，说明不合格：

- 读者只能说出项目有哪些文件，不能解释系统如何工作；
- 读者理解目标，却无法预测异常或高风险情况；
- 文档充满“无特殊处理”“暂无限制”等空章节；
- 同一事实在多个模块重复解释；
- 函数改名或局部重构导致大量正文失效；
- 文档只宣传能力，不说明失败和边界；
- 文档详细到接近源码逐句翻译。

最终目标是：

> 人类不需要掌握代码如何逐句执行，但能够掌握每个机制为什么存在、如何参与系统、依据什么作出决定，以及它在什么情况下可能失效。
